# mcp-imagegen V4 · 产品分析与改造说明

日期：2026-10-13　范围：`mcp-imagegen`（vivo 生产 192.168.3.35:8000）
性质：**先产品、后技术**。本文件第一节到第三节是产品判断，第四节起才是实现。

---

## 一、用户与场景（我们到底在给谁做）

**主用户**：本机使用者（非科班，三条业务线：无人零售设备 / 咖啡机外贸 / AI 自动化）。
**次用户**：接在这个 MCP 上的 Agent（DSH、WorkBuddy 等）——它们是**实际调用者**，
但**不是需求方**。Agent 只是把人的意图翻译成工具调用。

**真实场景（有据可查，非假设）**：
> 2026-10-12，用户要给「二代冰淇淋机器人」做产品宣传物料。参考图在
> `Y:\智能无人设备资料\渲染图\二代冰淇淋机器人渲染图\`，要求「基于参考图生成宣传图/视频」。

**当时发生了什么**：
- 服务只支持文生图 → Agent 只能**人肉读图、把视觉特征写成文字提示词**
  （"白色立式自助机、圆角机身、玻璃窗内白色六轴机械臂…"）。
  这是**有损转换**：细节丢失、比例靠猜、每次结果不可复现。
- 服务只支持文生视频 → 想要"让这张渲染图动起来"，**根本做不到**。
- 视频生成连试 1 小时 43 分、20 次全失败（503 队列满 + 429 限流），最后放弃。

**结论：上一轮不是"没做好"，是"能力缺位"。** 用户当时的需求，这个服务一个都没接住。

## 二、痛点排序（按"用户损失"排，不按"技术难度"排）

| # | 痛点 | 用户损失 | 现状 | 上游是否支持 |
|---|---|---|---|---|
| **P0-1** | **参考图生图缺失** | 有图不能用，只能口述特征，**成品不像、不可复现** | ❌ 无此参数 | ✅ `image` 字段（实测 base64 可用） |
| **P0-2** | **图生视频缺失** | 想让静态图动起来，**完全无路径** | ❌ 硬编码 `mode="text"` | ✅ `mode=keyframe` + `first_frame` |
| **P1-3** | **视频提交"撞墙即放弃"** | 上游队列满是**常态**（RPM=1），失败直接甩给 Agent 盲试，**白烧额度、白等 1.7 小时** | ❌ 立即返回 error | ✅ 服务端可代为排队 |
| **P1-4** | **工具面不可见** | 生产有 4 个工具，Agent 只看到 3 个，`list_video_tasks` 形同不存在 | ⚠️ DSH 缓存陈旧 | — |

**排序依据**：P0 是"能力缺位"（用户做不成事），P1 是"体验与可靠性"（做成了但难受）。
先把做不成的事做成，再优化做成的事。

## 三、产品设计决策（关键取舍）

### 3.1 「参考图」怎么传给上游？——这是本轮最大的技术死结

**死结**：上游 上游服务提供方 在公网，我们的服务在内网 `192.168.3.35`。
实测上游**拒绝内网地址**：
```
image must be a public http(s) URL or valid image base64: private URL host is not allowed
```
用户本机的 `Y:\...` 参考图，上游更不可能抓到。

**三条出路与取舍**：

| 方案 | 可行性 | 取舍 |
|---|---|---|
| A. 传公网 URL | 需要图先上公网 | ❌ 用户图在本地/内网，多一步外传，还涉及资料外泄 |
| B. 传 base64 内联 | ✅ **实测可用** | ✅ 采纳：图不过第三方存储，一步到位 |
| C. 服务端读本地路径 | 服务在 vivo，读不到用户 Y 盘 | ❌ 不可行 |

**决策：以 base64 为主通道**，并区分三种输入形态（对用户透明）：

1. **公网 URL** → 原样透传（上游自己抓）
2. **data URI / base64** → 原样透传
3. **我们自己的产物**（`/files/xxx.png` 或裸文件名）→ **服务端读本地文件、转 base64 再发**
   ← 这条是**关键产品设计**：它让「生成 → 挑一张 → 让它动起来」形成**零摩擦闭环**。

### 3.2 为什么"自己的产物"这条最重要

用户真实工作流不是"一次生成到位"，而是**迭代**：

```
生成宣传图 → 挑一张满意的 → 微调（换场景/换风格）→ 定稿 → 让它动起来做视频
```

这条链上每一环都依赖"把上一环的产物当输入"。
**若不能用自己的产物当参考图，用户就必须把图下载到本机、再想办法传回上游——闭环断裂。**

我们服务本来就有 `/files/` 静态服务和 IMAGE_DIR，
所以**服务端完全有能力自己读自己的产物**，转 base64 是顺手的事，对用户零成本。

### 3.3 图生视频：为什么主推 `keyframe` 而不是 `reference`

上游两个模式语义不同（官方文档）：

| 模式 | 语义 | 结果可控性 |
|---|---|---|
| `keyframe` | 输入图**作为成片真实首帧/尾帧** | ✅ 构图可控——"让这张图动起来" |
| `reference` | 输入图仅作**风格/内容参考** | ⚠️ 会**重新构图、重新安排时序**，主体一致性无保证 |

**产品判断**：用户说"让这张渲染图动起来"，要的是**这张图**，不是"类似感觉的另一个视频"。
所以**主推 `first_frame`（keyframe）**，`reference` 作为补充能力同时提供但不做默认。

### 3.4 视频排队：从"甩锅给 Agent"改成"服务端兜住"

**现状问题**：上游视频队列满是**常态**（免费额度 RPM=1，且队列长期满载）。
现在的行为是：撞到 503 就立刻返回错误 → Agent 拿到 `retry=yes` → **盲目重试**
→ 20 次全失败、烧 1.7 小时（10-12 实录）。

**这是把上游的排队问题，转嫁成了用户的等待成本。**

**决策**：服务端**代为排队**。撞到队列满时，不返回错误，而是：
1. 立刻给用户一个 `task_id`（本地排队号）+ `status=queued`
2. 后台按退避策略持续尝试提交（尊重 RPM=1）
3. 一旦提交成功，自动转入原有轮询流程直到出片
4. 用户随时用 `query_video` 查进度，**不需要自己重试**

**产品价值**：把"用户/Agent 反复手动重试"变成"提交一次，好了来拿"。

## 四、技术实现

### 4.1 新增模块：`infra/refs.py`（参考图解析）

把用户给的"参考图"统一解析成**上游可接收的形态**：

| 输入 | 处理 |
|---|---|
| `https://public-host/...` | 原样返回（上游自取） |
| `data:image/...;base64,...` | 原样返回 |
| `/files/<name>` / 裸 `<name>`（匹配落盘命名） | **读本地文件 → data URI** |
| 服务端可读的本地绝对路径 | 读文件 → data URI |
| 其他（含内网 URL） | `invalid_params`，明确告知原因 |

配套：大小上限（`REFERENCE_MAX_MB`，默认 10MB）、扩展名白名单、
读取失败 → `invalid_params`（**不静默降级**：参考图丢了还硬生成，等于骗用户）。

### 4.2 `generate_image` 参数扩展

```
image   string[]  可选  参考图（图生图/多图合成）；URL / base64 / 本服务产物
```

- 传了 `image` → 走上游**图生图（i2i）**；不传 → 文生图（原行为不变）
- `image` 与 `batch_size` 可并存（每张各自带参考图）
- 参考图 + `ratio`/`size` 规则不变

### 4.3 `generate_video` 参数扩展

```
first_frame       string    可选  首帧图（keyframe 模式）——"让这张图动起来"
last_frame        string    可选  尾帧图（keyframe 模式，需与 first_frame 至少一个）
reference_images  string[]  可选  参考图（reference 模式，最多 5 张）
```

**模式自动判定**（对用户透明，避免手填 mode 出错）：
- 有 `first_frame`/`last_frame` → `keyframe`
- 有 `reference_images` → `reference`
- 都没有 → `text`（原行为）

**互斥校验**：keyframe 与 reference 字段不可混用（上游会 400，我们在本地先拦，
给出 `invalid_params` 契约行而不是让用户看上游报错）。

### 4.4 视频提交排队（`app/video_pipeline.py`）

作业新增"提交前"阶段：

```
提交成功 ────────────────────────────→ 轮询 → 终态
提交撞队列满 → 本地排队号 + 后台代排队 ─┘（提交成功后自动接上）
```

- `JobEntry` 增 `upstream_id`：本地排队号与上游 video_id 解耦
- 后台 worker 先做"带退避的提交重试"（上限 `VIDEO_SUBMIT_QUEUE_WAIT_SEC`，默认 600s），
  成功后转原有轮询逻辑
- `query_video` 对排队中的作业返回 `status=queued`（非错误）
- 排队超时 → 明确失败原因（不是静默消失）

### 4.5 参考图上传端点（`POST /upload`）

给"本机参考图"（Y 盘那种）一条零上下文成本的通道：
Agent 用一条 `curl --data-binary @图.png` 上传 → 拿到 `/files/<name>` → 当参考图用。
Bearer 鉴权与 `/mcp` 同 token；沿用落盘命名与大小校验。

## 五、验证策略（测试 + 用户视角）

**分三层，缺一层都不算做完**：

| 层 | 手段 | 判据 |
|---|---|---|
| 单测 | pytest（容器内跑全量） | 全绿，且新增用例覆盖：参考图解析各形态、模式判定、互斥校验、排队生命周期 |
| 真实链路 | 打生产 `/mcp` 端到端 | 图生图出图、图生视频出片、排队路径可观测 |
| **用户视角** | **用用户原话的场景做验收** | "拿一张参考图 → 生成宣传图 → 让它动起来"**全程走通** |

**用户视角验收是本轮的硬门槛**：技术上 200 不等于产品上可用。
必须复现 10-12 那个真实场景并跑通，才算补上了当初缺的能力。

## 六、不做的事（明确划界）

- ❌ 不做公网图床/外传：参考图不经第三方存储
- ❌ 不做自动删图（沿用规格书红线）
- ❌ 不做上游参考视频/参考音频（`videos`/`audios`）——用户当前无此需求，避免无谓复杂度
- ❌ 不改熔断参数（规格书红线）
