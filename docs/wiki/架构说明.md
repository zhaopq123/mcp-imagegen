给想改代码或排查问题的人看的。

## 总览

```
客户端（AI Agent）
    │  MCP streamable-http + Bearer 鉴权
    ▼
┌─────────────────────────────────────────┐
│ server.py                                │
│  uvicorn :8000                           │
│   ├─ BearerGate        ← /mcp 鉴权       │
│   ├─ /healthz          ← 健康检查         │
│   ├─ /files/<name>     ← 转存产物下载     │
│   └─ FastMCP（三工具）                    │
│       ├─ generate_image                  │
│       ├─ generate_video                  │
│       └─ query_video                     │
└─────────────────────────────────────────┘
    │
    ▼ httpx
Agnes AI 上游（api.agnes-ai.cn）
```

## 分层结构

```
app/       应用层：工具定义、流水线、端点、对外契约
engine/    引擎层：错误分类、模型路由、响应归一化
infra/     基础设施层：API 客户端、槽池、熔断、转存、任务表
ops/       运维层：存活通知、优雅停机、日志
config.py  配置：加载 + 嵌套不等式自检
server.py  入口：装配 + 启动
```

**分层规则**：上层可以调下层，下层不认识上层。
`app` 是唯一知道"MCP 工具长什么样"的层；`infra` 只知道"怎么跟 Agnes 说话"。

## 一个生图请求的完整旅程

```
1. 客户端 → POST /mcp（tools/call: generate_image）
2. BearerGate 校验 token
3. tool.py 收到参数，调 validate_params 校验
4. pipeline.py：
   a. 槽池（budget.py）拿一个并发槽 —— 没槽则排队，30s 超时返回 busy
   b. 熔断器（circuit.py）查状态 —— OPEN 则直接快失败
   c. router.py 定模型（唯一模型，恒 auto）
   d. agnes.py 发 HTTP 请求到上游
      ├─ 成功 → 拿到图片 URL
      └─ 失败 → 记录失败（可能触发熔断），按重试纪律重试一次
5. persist.py（如果 persist=true）：
   下载图片 → 存到 IMAGE_DIR → 生成 /files/<name> 链接
6. normalizer.py 归一化响应 → 生成 meta 行
7. 返回给客户端
8. 释放槽池
```

## 关键设计决策

### 为什么超时用"嵌套不等式"而不是各管各的

早期版本各层超时独立配置，出现过内层等 120 秒、外层 100 秒就放弃的情况——
内层资源还在占用，外层已经在重试，造成浪费和混乱。

现在：`read ≤ 分档 ≤ 总预算 < Agent建议 < 优雅停机`，
启动时校验这组关系。改任何一个超时，启动时就知道会不会破坏整体。

### 为什么熔断分硬软

- **硬熔断**（429/402）：上游明确拒绝，再试毫无意义，600 秒内直接快失败。
  省下的是每次请求都要等上游响应的时间。
- **软熔断**（连续失败 2 次）：可能是网络抖动，300 秒观察期后放探针试探。

两者分开计数，恢复条件也不同。

### 为什么转存（persist）是可选的

上游返回的图片 URL 是临时的（约 1 小时过期）。
转存 = 下载到自己的服务器，提供长期链接。

但这需要额外的下载时间和磁盘空间。
所以做成参数：要长期保存就 `persist=true`，只要临时看一眼就 false（更快）。

### 为什么视频要单独的任务表

视频生成 5–10 分钟，远超单请求 200 秒预算。
所以设计成：提交 → 立刻返回 task_id → 客户端用 query_video 轮询。

任务表是内存态（TTL 2 小时，上限 100 条）——重启即失。
这是刻意取舍：任务表如果持久化，就要处理"服务重启后任务状态与上游不一致"的问题，
复杂度大增，而 2 小时足够客户端完成轮询。

### 为什么用单文件 client + 指针轮换

`agnes.py` 里的 AgnesClient 管理底层 httpx.AsyncClient。
每日 04:00 重建客户端（rotate），新旧客户端用指针切换，
旧客户端等在途请求归零后再关闭（最长 300 秒）。

这样避免了"重建时杀掉正在处理的请求"。

## 线程纪律（R2 铁律）

**整个服务只用 asyncio，不开任何线程。**

原因：
- 线程间的状态共享需要锁，锁用错了就是死锁
- watchdog 心跳依赖事件循环，开线程会让"事件循环僵死"的判定失效
- 有专门的单测（test_no_threads.py）扫描源码确保没有 threading/thread 用法

所以看到"后台任务"，都是 `asyncio.create_task`，不是线程。

## 优雅停机流程

```
SIGTERM
  → uvicorn 停收新请求
  → 在途连接排空（timeout_graceful_shutdown=220s）
  → lifespan shutdown：
      ├─ 取消心跳 / 每日重建 / 任务清理 三个后台协程
      ├─ coordinator.begin_shutdown()（STOPPING=1 + 日志）
      ├─ 等待在途请求收尾（最长 220s）
      ├─ api_client.aclose()
      └─ persist.aclose()
  → 进程退出
```

对应 systemd 的 `TimeoutStopSec=220`——超时未退由 systemd SIGKILL 兜底。
